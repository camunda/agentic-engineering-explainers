Get to the eleventh

Nobody one-shots good software. The first spec produces a prototype, and the real shape shows up as you use it. Plan for the first ten versions to be wrong, and get to the eleventh as fast and as cheaply as you can.

scroll ↓
The naive model

A spec is a hypothesis. The first build is how you test it.

“One-shotting” imagines a perfect spec going in and finished software coming out. But most of what a product needs is unknown until something exists to try. The spec is an input to the first version and an output of the later ones: each round makes it sharper.

So the prototype isn’t the end. It has to be questioned, proven and refined. Agents don’t remove that work. They make each round cheap enough to do many of them.

One-shotting

Spec→Prompt→Done

Works for small, well-known problems. For anything new, “done” is a prototype that nobody has used yet.

Crafting

Spec→Prototype→Question→Prove→Refine↺Publish

The dashed steps repeat. Each round changes the code and the spec, and records what was learned.

Correct is not the same as right

Guardrails settle correctness. Fitness still takes rounds.

There are two questions about every version. Does it do what we said? And is what we said the right thing? The first can be made deterministic. The second can’t.

That is what the guardrails are for. When correctness checks itself, attention is free for the question no guardrail can answer.

Where the speed comes from

The speed-up is in the cost of a round, not in typing faster.

If the first ten versions are going to be wrong, what matters is how long it takes to get through them, and how much human attention each one uses.

Faster code alone doesn’t get you there. If every version still waits for a person to check that it works, the person becomes the queue. Guardrails take correctness off that person’s plate, and a network of consumers does the first pass on fitness. Then a round costs hours, and the human time goes into judging the result.

The step you can’t take back

Prove it before you publish.

Not every version is cheap to throw away. Once an API is published, people build on it, and changing it breaks them. So the rounds have to happen before publishing.

For an API, fitness means ergonomics: can someone use it for real work without fighting it? You only find out by using it. So implement it, then consume it from several different integrations. Each integration is a first user. Every awkward call, workaround and wrong first guess is feedback that arrives before anyone outside depends on the API.

User testing at scale by proxy

Many consumers make all fitness problems shallow.

“Given enough eyeballs, all bugs are shallow.” The same works for fitness, with the eyeballs replaced by a network of integrations. One engineer can run it: agents write the API, then agents write the integrations that consume it.

For the Camunda SDKs, the network is the seven SDKs generated from the API spec and the harnesses built on top of them. Choose a consumer to see what it found before (or soon after) release.

The rule

Scale the network with the velocity.

Agents raise the rate at which features ship. Every feature brings its share of defects and fitness problems. If the number of consumers stays the same, the share they catch stays the same, and everything else lands on users.

So when the code speeds up, the integration and scenario network has to grow with it. That is cheap to do, because agents write the integrations too.

An illustrative model, not a measurement: each feature brings one problem, and each consumer independently catches a quarter of what reaches it.

Know what the proxy can’t tell you

Proxies aren’t users, but friction can be measured.

Agent consumers find friction fast: calls that take too much setup, names that mislead, operations that are easy to misuse, things that are missing. They don’t share your users’ goals, and they share blind spots with the agents that wrote the API. The proxy network gets you to version eleven before publishing. Real users and production telemetry judge it after.

Humans decide

  • Which consumers matter: the integrations that stand in for real users.
  • What “better” means: the friction to drive down, and what must not get worse.
  • When to stop: when a round no longer teaches anything, publish.
  • What can’t be undone: which steps need a fence, a flag or a preview first.

Agents do

  • Build each version, and the integrations that use it.
  • Record the friction: glue code, workarounds, retries, wrong first attempts.
  • Feed what the consumers found back into the spec.
  • Write down what each round taught, so the throwaway code isn’t wasted.
So

Versions are disposable. What they teach is not.

Don’t expect to one-shot it. Make correctness deterministic so it costs no attention, build a network of consumers that uses each version before anyone else does, and grow that network as fast as the code. Then go through the wrong versions quickly and cheaply, and publish the eleventh.
