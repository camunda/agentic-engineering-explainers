The Cambrian explosion

Until June 2025, one engineer maintained one SDK by hand. Then we went agentic. That engineer scaled up, and then the approach scaled out to the people around him. Here is what happened, measured from the git history of the 22 repositories it grew into, comparing the 12 months before with the last 12. Then two more Camunda engineers, who got there on their own. Nobody taught them this approach: we found them when we started looking at how to expand it across the organisation, and each had taken a different path. Last, a shared tool where the method left the SDKs and many people grew a product inside it.

Case study 1 · Engineer A · Before

One repository, tended by hand.

From late 2023 to May 2025, the Camunda 8 JavaScript SDK (camunda-8-js-sdk) was maintained manually. It was a healthy, well-used project, and it moved at the speed of one person with a day job.

Every feature, test and release went through the same pair of hands.

Stage 1 · Harden the foundation

The first thing we built wasn't an SDK. It was a better spec.

Agents generate from what you give them. So before generating clients, we made the OpenAPI specification say what the API means: domain types for keys, eventual consistency marked on every endpoint that has it, and lint rules to keep it that way.

That is derivation over duplication applied to a whole product line: one source of truth, everything else generated from it.

Stage 3 · Harden the tests

Speed needs a signal you can trust.

Seven SDKs at agentic speed only work if “green” means something. So the tests were derived from the spec too: response bodies asserted against the schema, then whole test suites generated from a semantic graph of the API.

The test generator became the most collaborative repository in the story: ten people have committed to it.

Then the SDKs were tested against each other. A conformance harness wraps all seven SDKs in thin adapters, sends the same operation to each, and compares the HTTP requests they would send. Seven SDKs must agree on every operation in the spec.

Stage 3, continued · Profile every workload

“Profile your workload” was the only honest answer. Now we profile all of them.

Customers ask how to deploy their workers: how many processes, how many workers in each, REST or gRPC streaming, which SDK. Before, the honest answer was “profile your workload”. Nobody had the time to measure every combination for even one SDK.

At agentic speed, the measurement is the cheap part. A performance matrix runs every valid combination of worker topology, SDK language, SDK mode, handler type and cluster size, locally or on Google Cloud, and publishes the results to a dashboard.

The answers are now specific. Prefer streaming when you run many workers: its tail latency stays flat while REST long-polling climbs. Spread workers across processes, about one event loop per core, instead of adding workers to one process. Set the C# poll interval to 25 ms: in the Google Cloud runs, that alone took throughput from 117 to 146 jobs a second.

The matrix also feeds the SDKs: it produced the proposal for threaded workers in the JavaScript SDK. For the method behind it, and how the conformance harness works as an oracle, see Point them at a number.

Up, and out

It wasn’t one person getting faster. Other people learned it too.

An approach that only works for the person who invented it is a trick. This one transferred: to a student who learned it from scratch, and to a team that took a whole repository over.

From work experience to SDK co-owner

She joined as a student intern on work experience and learned agentic engineering from scratch. She is now an engineer on staff.

  1. Mar 2026: first commits. README examples and fixes across the JS, Python and C# SDKs, with a lot of “address review feedback”.
  2. May 2026: first change to shared tooling (schema-bundler).
  3. Jul 2026: leads the Go SDK. 123 of its 137 human commits are hers.
  4. Sep 2026: leads the Java SDK. 64 of 72.

870 commits and 167k authored lines across 9 repositories in eight months. She is now a co-owner of the SDKs and the principal driver of several of them.

The QA team took over the test generator

api-test-generator was built in April and May. In June it changed hands. Since July, every commit has come from the QA team and its contributors.

Original engineerQA team & contributors
  1. The QA team runs its own automation on it, pinning the spec and opening PRs.
  2. Four student interns contribute too. Their open pull requests extend it to generate SDK test suites for JS, Python and C#.

From one owner to a pod of three

Before going agentic, one engineer owned the SDK. Now the SDKs have an SDK pod of three people. The former intern co-owns them and drives several. A third engineer brings the human bus factor down, and supports the SDKs in production with an agent that picks up production issues, so a report from the field becomes a fix without pulling the others off their work.

Reading the numbers honestly

Volume isn’t value. But these numbers survive the obvious objections.

“It’s generated code.”Excluded. Generator output, vendored specs and lockfiles are not counted: another 3.2 million generated lines sit on top of these numbers.
“Agents just make smaller commits.”The opposite. The median commit grew from 29 changed lines to 157. The commit ratio understates the change.
“The team got bigger.”It did, and that is part of the result. The same engineer alone went from 182 commits a year to 3,649, and everyone else together added another 1,300. Try the switches on the chart.
“Lines of code are a bad measure.”Agreed, so look at what shipped: releases of the published packages went from 59 a year to 438, across seven languages instead of one.

Case study 2 · Engineer B

A product in five weeks, inside a fence.

Engineer B works on the SaaS console and its operations tooling, and went agentic independently of Engineer A. Before agents, B already shipped in small, fast steps: about 34 pull requests a month, a median of 33 changed lines, nearly all approved by a colleague.

From late 2025 the rate tripled, to about 100 a month, and the pull requests grew to a median of 76 lines. Colleagues still approved 94% of them.

Then B ran an experiment: build a whole product from a written plan, in one go, in a private sandbox repository. One of the first pull requests added the CI gates. After that, every pull request carries a task ID from the plan, and each one merged through those gates.

The fence mattered. No person reviewed the sandbox, but in the same months B’s work in shared repositories was still 75% approved by a colleague. Zero eyes where the blast radius is contained; human review where it is not.

Case study 3 · Engineer C

Each PR waits longer. More of them get through.

Engineer C maintains a deployment repository that many teams depend on, and went agentic independently too. Every change there is reviewed by another maintainer, and nobody wanted to change that.

From April 2026 C went agentic. C’s pull requests in that repository went from 10 a month to 47, and they got bigger. The review rule held: colleagues approved 98% of them.

The median time from open to merge went from 11 hours to six days. That looks like a slowdown. It isn’t: merged pull requests went from 9 a month to 34. Time to merge measures how long one change waits. Throughput measures how much gets done.

The reviewers scaled too. Human reviews of C’s pull requests went from 14 a month to 69, five times as many. The queue of open pull requests grew from a handful to between 10 and 30, and it drains: it does not grow month on month. That is a longer queue, not a backlog.

The wait has three parts. A first review now comes after about a day instead of a few hours, because reviewers batch their work. Most changes now get a round of comments. And after approval, a change waits about 19 hours instead of 2 for CI and the merge queue. More pull requests were also closed without merging, as approaches were tried and dropped.

The risk is concentration: two reviewers do most of the reviews. C’s answer was to work on the gate, not around it. C reviews as much as C writes, and built tools for the queue: a multi-agent PR reviewer with domain checks, a test bed for merge-queue races, and a CLI for running agents across many repositories.

Who decides a change is done?

An agent loop, a human signature, or a human review.

All three engineers use agent reviewers. What differs is who decides that a change is finished. That explains the different times to merge.

A · The loop decidesAgent reviewers and the coding agent loop until the findings converge: a median of 2 review rounds, and a quarter of PRs take 4 or more. 90% of merged PRs show the loop, and 80% merged with no human review at all. The tests and the loop are the gate. An automatic approver runs in shadow mode beside it. Time to merge: under an hour.
B · The loop decides, a human signsThe same pattern: 91% of PRs show an agent loop, with agent verdicts posted as structured comments. A colleague approves 77% of PRs, but 94% of those approvals carry no comment, and they arrive within an hour of the last agent round. The signature is a formality. Time to merge: under two hours.
C · The human decidesAgents do one first pass on 60% of PRs. Then a colleague reviews for real: on half the PRs they comment or ask for changes, and they approve about a day after the last agent round. The human queue sets the pace. Time to merge: days.

None of these is wrong. Where a change can break other teams, C’s gate buys safety with time. Where the loop is trusted, a human signature costs little, and it adds little. The choice should be deliberate, per repository.

Source: merged pull requests in Camunda’s GitHub organisation, May – October 2026 (C from April). An agent round is a review by an AI reviewer, or a comment that an agent posted: a verdict, a review report or an “addressed in <commit>” reply. Loops that ran before the PR was opened are not visible, so these numbers undercount them. A comment-free approval can still follow a careful read; the short gap after the last agent round is the stronger signal.

Case study 4 · c8ctl · A shared garden

The method leaves the SDKs.

c8ctl is the Camunda 8 command-line tool. It is not an SDK, and it was not started by Engineer A. That makes it the test of whether the method is general: here it left its original domain, and other people grew a product inside it.

Its originator started with a clear vision, down to the user experience: every command is a verb and a resource, like c8 list pi. He committed that vision first, as a plan, agent instructions and the API spec. Then he set up CI on a matrix of versions and let a coding agent run at full speed. The first day ended with every command implemented, tests, docs and a 1.0.0 release.

Integration testing was done by users, with the originator as user zero. Today every merge publishes to an alpha channel straight away. When nobody reports a problem against an alpha, it is promoted to stable.

Case study 4 · What the registry changed

The bugs moved from missing parts to the edges.

Before the registry, users found commands with parts missing: a get that did not exist, a flag rejected by every search command, a flag accepted and then ignored. When one was patched, the next one was still possible to write. #256 says so: the instance was fixed, “but the pattern is still expressible”.

After April, one built-in report of this kind remains (#441). The rest are at the edges the registry did not cover yet: plugins, verb aliases, flag parsing and shell completion. Each got a structural fix rather than a patch: a plugin contract, and two-stage flag parsing that scopes every flag to its verb (#373).

Source: issues in camunda/c8ctl, open and closed, to October 2026, classified by hand. Built-in: a command, flag or help entry that was declared but missing or not wired (#41, #43, #111, #246, #256, #441). Edges: the same kind of gap in plugins, aliases, parsing or completion (#358, #363, #364, #407, #593, #597, #638). The numbers are small; the chart shows where the bugs are, not a rate.

Case study 4 · Many gardeners

The structure tells new contributors where things go.

28 people have filed issues and 26 have committed. Most arrived after the hardening, and they arrive with features, not with questions about where to put them.

They add what they needTeams added the commands their own work needed: wait states (#437), Business IDs (#438), job custom headers (#447), physical tenants, suspend and resume, and process-instance migration and modification (#628, #674).
They build to the structureOne contributor asked for the cluster plugin to “declare flags instead of re-reading process.argv” (#593). Another made plugins declare the c8ctl version they need (#523). A third built an element-template migration engine in about ten small, typed, tested slices, and wrote its bugs up as defect classes (#643–#660).
They run the method themselvesThe originator designed an agentic pipeline with an implementer, two independent reviewers and a deterministic merge coordinator (#577). Another engineer turned an audit into tickets for red/green checks on fixes, coverage ratchets and reports of runs that pass only on re-run (#664–#670).

An automated repository audit in July, run by an agent skill, called c8ctl “a near-exemplar of LLM-velocity engineering discipline” (#474). The same audit found the gap. The philosophy is “if it is green, it merges”, but main has no active branch protection: the ruleset exists and has never been enabled, so whoever merges checks by eye that about 84 checks are green, and agent pull requests wait for a manual click before CI runs. The October follow-up turned that into tickets (#664, #670). Until they land, the merge gate is a habit, not a fact. The merge button is part of the system.

Source: git history, issues and releases of camunda/c8ctl, and npm download counts for @camunda8/cli, to October 2026. Branch protection checked on the repository in November 2026.

So

The explosion came from the structure, not from the agents alone.

Engineer A hardened the spec first, derived the SDKs and the tests from it, used the new capacity to measure what nobody could measure before, then taught the approach to an intern and a QA team. One owner became a pod of three. Engineer B put the gates in first and fenced the experiment off, so it could run with zero eyes. Engineer C kept the human gate on shared code. Each change waited longer, but the reviewers scaled with the volume, so the queue grew without becoming a backlog, and C started building tools for the gate. In c8ctl, a one-shot became a structure that 26 people now build in, and the next step is to make its merge gate a fact.

All three got faster. What they built around the agents decided where that speed went.
